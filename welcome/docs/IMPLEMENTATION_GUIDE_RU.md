# Welcome Moscow: реализация и проверка по шагам

## 1. Что именно строим

Девять функциональных модулей: M1 каналы/вход/кабинет; M2 ИИ/база знаний; M3 каталог/брони; M4 платежи; M5 обслуживание; M6 консьерж; M7 CRM/удержание; M8 корпоративные клиенты; M9 инфраструктура/аналитика. Голос — отдельный этап расширения M1, а не десятый бизнес-модуль.

12 скачанных проектов — набор кандидатов. Не нужно устанавливать все одновременно. Основной путь: Chatwoot, EspoCRM, LangGraph, PostgreSQL/pgvector, Celery, Keycloak и Superset. LiveKit подключаем позже. Dify — альтернатива ИИ-слою, n8n — вспомогательная автоматизация, QloApps — кандидат на замену PMS, ERPNext — возможное расширение корпоративного учёта. В первом пилоте не разворачиваем Dify/QloApps/ERPNext рядом с основным путём без отдельной задачи и причины.

Codex, Claude Code и Cursor помогают создавать код. Они не являются сервером проекта и не заменяют внешние API. Инструмент разработки можно сменить без смены архитектуры. Выбирать основной инструмент по проверке одинаковых задач; передача между инструментами только через коммит и актуальную документацию, а не одновременное редактирование одной ветки.

Здесь 90 РАБОЧИХ дней, без привязки к календарю. Это последовательность и ориентир, не гарантия срока. Один разработчик может потратить больше. Внешние доступы, качество данных и обнаруженные ошибки сдвигают зависимые этапы. Готовность к 10 000 квартир, 10 млн профилей и 10 000 диалогов в сутки доказывается измерениями; день 90 сам по себе её не подтверждает.

## 2. Простые определения

- API: согласованный способ запросить данные или выполнить действие в другом модуле.
- Контракт: точные поля запроса, ответа, ошибки и события.
- Миграция: записанное изменение структуры базы, которое можно повторить на другом стенде.
- Ветка: отдельная линия изменений в Git.
- Коммит: сохранённый набор изменений.
- Mock: имитация внешнего сервиса для тестов; не доказательство работы реального провайдера.
- Staging: тестовый сервер, отдельный от рабочего.
- Smoke test: короткая проверка, что установленная версия запускается и выполняет основные действия.
- Idempotency: повтор одного запроса не создаёт вторую бронь или оплату.
- UNKNOWN: действие могло исполниться, но результат ещё не установлен.
- CI: автоматические проверки каждого набора изменений.

## 3. Организация файлов и ответственности

programs/ содержит неизменённые сторонние проекты. Собственный код создаём отдельно: services/welcome-api/ с каталогами modules/identity, ai, booking, payments, operations, concierge, crm, corporate; apps/guest-portal/; contracts/; migrations/; tests/; deploy/; docs/. Это предлагаемая структура, ещё не созданная реализация.

На старте собственные бизнес-модули могут работать в одном приложении FastAPI. Фоновые процессы worker и scheduler запускаются отдельно. Chatwoot, EspoCRM и Keycloak разворачиваются отдельными приложениями. Подмодули Git не равны микросервисам.

## 4. Как не допустить наложения задач

1. Для каждой задачи заводим номер, цель, модуль, зависимости, разрешённые файлы, критерии проверки и способ восстановления.
2. Статусы: BACKLOG → READY → IN_PROGRESS → REVIEW → TESTED → DONE. Отдельно BLOCKED с описанием зависимости. DONE означает код, проверки и документацию.
3. По умолчанию одна активная задача на ветку. Не поручаем двум ИИ менять одни файлы или общую миграцию.
4. Используем ветки codex/<номер>-<название>. До начала читаем git status, не перезаписываем чужие незавершённые изменения.
5. Сначала фиксируем контракт, затем реализацию. Изменение общего контракта или БД — отдельная задача с проверкой потребителей.
6. Сторонние исходники не редактируем ради нашей бизнес-логики. Используем API, официальные расширения и собственные адаптеры.
7. Модуль не пишет напрямую в таблицы другого модуля. Использует его сервис/API. Отчёты читают подготовленную витрину.
8. Каждый процесс имеет отдельные секреты и минимальные права. .env не попадает в Git.
9. Ошибки приёмки блокируют объединение. Независимые задачи можно продолжить; неисправный модуль не объявляем готовым.
10. В конце дня сохраняем коммит, отчёт о проверках и следующую задачу. Никаких обещаний «всё работает» без результата теста.

## 5. Ежедневный порядок для новичка

Утром откройте основной проект, прочитайте docs/STATUS.md и выберите одну READY-задачу. Попросите ИИ сначала перечислить зависимости и критерии проверки. После реализации запустите проверки, посмотрите diff и проведите короткую ручную проверку. Затем сохраните коммит, обновите статус и запишите результат.

Шаблон задания ИИ:

> Задача WM-XXX. Модуль M_. Цель: ... Предыдущая принятая версия: ... Разрешённые файлы: ... Используй контракт версии ... Критерии готовности: ... Сначала проверь зависимости и состояние Git. Реализуй задачу, проведи необходимые проверки, покажи результат и ограничения. Если требуется изменить общий контракт, оформи это отдельно. Не включай внешние операции без реально доступного адаптера.

Проверка каждого модуля проходит шесть ступеней: изолированная логика → контракт → интеграция с тестовой БД/очередью → согласованный sandbox провайдера → сквозной сценарий → нагрузка/сбои. Если sandbox отсутствует, реальные тесты проводят на согласованных тестовых данных с установленным порядком очистки.

## 7. Отдельная приёмка каждого модуля

### M9. Инфраструктура и аналитика

Подготовка: разные development/staging/production, отдельные БД и секреты. Сперва контейнеры, БД, health, CI и бэкапы; позже витрины и Superset. Тест: создать тестовую запись, сделать бэкап, восстановить на другом экземпляре и сверить. Остановить worker — задача остаётся в долговечном журнале. Отчётная система не меняет брони. Для KPI заранее определить формулу и контрольный пример. Готовность: повторяемый запуск, успешное восстановление, наблюдаемые ошибки и измеренные показатели.

### M1. Каналы, вход и кабинет

Подготовка: два разных тестовых гостя, сотрудник, web/Telegram. Сперва identity, затем каналы, кабинет и голос. Тест: гость A не получает бронь B; одинаковое имя не объединяет профили; истёкшая сессия не действует; повтор сообщения не запускает второй ответ; исходящее сообщение не создаёт цикл. В Chatwoot проверить ответ оператора при отключённом ИИ. Готовность: доступ подтверждён сервером, сообщения относятся к правильному диалогу, переключение на оператора проверено.

### M7. CRM и удержание

Подготовка: центральная модель профиля, поля согласий по целям/каналам, mapping EspoCRM. Сперва профиль/согласия; scheduler позже. Тест: повторный импорт не дублирует гостя; неизвестное предпочтение не превращается в FALSE; изменение разрешённого поля отражается по согласованному направлению; отзыв согласия подавляет уже queued маркетинг; новая бронь отменяет ненужное напоминание. Готовность: один главный профиль, доказательство согласия, исправная очередь и ручной просмотр сотрудником.

### M3. Каталог и бронирования

Подготовка: согласованный экспорт RC, sample webhook, ответы о поддерживаемом API, тестовые объекты. Сперва каталог/inbox/assisted заявки. Live цены и запись только при реально согласованном API. Тест: ошибки дат/вместимости; повтор и нарушение порядка webhook; неполный импорт; устаревшая цена; два запроса на одну квартиру; потеря ответа после создания; отмена и изменение. Готовность assisted: заявка REQUESTED, менеджер подтверждает. Готовность transactional: авторитетный источник подтвердил операцию, нет повторной записи после timeout. Локальная блокировка БД не блокирует продажи у внешних каналов.

### M5. Обслуживание и поддержка

Подготовка: исполнители, категории, severity, порядок эскалации и release policy доступа. Тест: неисправность → заявка → назначение → решение; тяжёлая проблема попадает ответственному; чужому гостю не выдаётся код; инструкция не выдаётся раньше разрешённого времени; запрос менеджера не принимается за выполненную компенсацию. Готовность: сотрудник видит заявку, может продолжить её без ИИ, гость получает фактический статус.

### M2. ИИ и знания

Подготовка: только утверждённые документы с версией/аудиторией; набор эталонных вопросов; модель выбирается по тесту. Подключать инструменты последовательно READ → заявки → разрешённые транзакции. Тест: известный FAQ, неизвестный факт, подмена прав, чужая инструкция, устаревшая цена, отсутствие API, передача оператору. Сервер запрещает действие независимо от текста модели. Готовность: опубликованный отчёт качества, стоимость диалога и задержка; отсутствие выдуманного подтверждения брони/оплаты.

### M6. Консьерж

Подготовка: ключ разрешённого API, тестовые адреса и предпочтения. Тест: правильная квартира/район; источник и время актуальности; недоступные часы работы не объявляются проверенными; отказ карт не блокирует бронирование. Готовность: полезная рекомендация с понятными ограничениями, независимость от финансовых операций.

### M4. Платежи

Подготовка: отдельные sandbox credentials, согласованная связь с RC/PMS и валюта. Тест: правильная сумма; поддельный webhook; повтор; частичная оплата; возврат; потеря ответа; платёж по чужой брони. Уведомление сверяется по способу, предусмотренному провайдером. Готовность: одна логическая операция, проверенный ledger, независимые статусы брони/оплаты/проживания. Реальные деньги не используются для проверки без специально согласованного сценария.

### M8. Корпоративные клиенты

Подготовка: две тестовые компании, разные роли сотрудников, лимиты и правила approval. Тест: превышение бюджета; доступ к чужой компании; approval на старую сумму; счёт/отчёт по фактическим операциям. Готовность: компания подтверждает точные условия, изменение требует нового согласования, отчёт доступен только уполномоченным.

## 8. Сборка и соединение

Python не требует одной общей компиляции всего набора. У отдельных приложений могут быть собственные сборки Python/Node/Java/PHP. Берём официальные образы стабильных версий, а собственное приложение и интерфейс собираем в отдельные образы. Образы не содержат секретов. Git подмодули — хранилище исходников; наличие всех папок не запускает систему.

Сначала замораживаем проверенные версии контрактов, миграций и образов. Далее: сборка → автоматические тесты → deploy в staging → миграции по документированному порядку → health → smoke → сквозные сценарии → нагрузка/сбои → ограниченный production rollout. Проверяем совместимость предыдущей и следующей версии при обновлении. Откат кода не отменяет исполненную бронь или платёж.

Порядок добавления связей:

1. M1 + M7: входящий подтверждённый гость → правильный профиль.
2. M7 + M3: профиль → квартира → заявка → отражённая бронь.
3. M3 + M5: подтверждённая бронь → заселение/обслуживание.
4. M1 + M2: сообщение → FAQ → ответ; затем инструменты поиска и заявки.
5. M2 + M6: местные рекомендации без изменения брони.
6. M3 + M4: подтверждённые операции бронирования и оплаты по согласованному workflow.
7. M7 + scheduler: разрешённое напоминание после повторной проверки.
8. M8 + M3/M4: корпоративные ограничения и approval.
9. M9 получает события всех модулей; аналитика не вмешивается в основной поток.

Каждое событие содержит event_id, schema_version, тип, время, разрешённые идентификаторы. Локальный факт и outbox сохраняются в одной транзакции. Получатель отмечает обработанные ID. Не обещаем exactly-once доставку: достигаем устойчивого результата при повторной доставке. Долгие внешние вызовы не держат открытую транзакцию БД.

## 9. Итоговые сценарии приёмки

Обычный путь: сообщение → подбор → подтверждение → бронь/заявка → платёж → подготовка к заезду → обращение → выезд → разрешённое напоминание → отчёт. Отдельно: отказ гостя, отмена, изменение цены, чужая бронь, дубль события, недоступная PMS, неуспешная оплата, UNKNOWN операция, отозванное согласие, голосовой канал и корпоративная поездка.

На нагрузочном стенде проверяем 10 млн СИНТЕТИЧЕСКИХ профилей, 10 тыс. объектов и согласованный пик. 10 тыс. диалогов в сутки не означает 10 тыс. одновременных диалогов. Отдельно измеряем тяжёлые отчёты, API limits, число токенов, очереди, p95, ошибки, блокировки и восстановление. Стресс-тест не должен создавать реальные брони или списания.

Условие запуска: обязательные сценарии проходят, критические дефекты закрыты, бэкап восстанавливается, провайдеры подтверждают результаты, оператор умеет продолжить работу при отказе ИИ. Невыполненное условие означает ограниченный пилот или перенос запуска. Абсолютное отсутствие ошибок обещать нельзя; задача процесса — обнаруживать и ограничивать их последствия.
